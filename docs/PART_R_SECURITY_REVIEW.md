### Part R Security Matrix

| Security Control | Current Implementation in SmartSakay Dagupan | Missing / Weak? | Proposed Improvement |
| :--- | :--- | :--- | :--- |
| **Input Validation** | Centralized Joi schema validation via `validate(schema)` middleware (`middleware/validate.js`). Enforces strict data types, string trimming, regex patterns (passwords, names, OTPs), minimum/maximum values, and Mongoose schema validations across auth, fare, route, and complaint routes. | Search query parameters (`req.query.search`, `category`) and URL path parameters (`req.params.id`) are not pre-validated with Joi schemas. In some routes (e.g. `createRoute`), `req.body` is passed directly rather than extracting whitelisted fields. | Implement Joi schemas for `req.query` and `req.params` (validating MongoDB `ObjectId` format). Apply payload destructuring/whitelisting in controllers to prevent mass-assignment vulnerabilities. |
| **Password Hashing** | Uses `bcryptjs` with an adaptive cost work factor of 12 (`saltRounds = 12`) implemented in the Mongoose `pre('save')` hook (`models/User.js`). Strips password hashes in `toJSON()`. Password comparison is handled via `user.comparePassword()`. | Direct Mongoose update methods like `findByIdAndUpdate` bypass the `pre('save')` hook (mitigated currently because password changes use dedicated routes with `.save()`). Default seeded credentials in development use static environment passwords. | Enforce that all credential mutations go through dedicated save pipelines. Add minimum password entropy validation and force password rotation upon first login for seeded administrative accounts. |
| **Authentication** | Multi-factor email verification using 6-digit OTPs (`models/Otp.js`) with 5-minute TTL, bcrypt code hashing, and a 5-attempt limit. Enforces account status check (`isActive`). Dedicated password reset flow and explicit server-side logout (`/api/auth/logout`). | When Gmail app password is not configured or in non-production environments, `authController.js` returns `devOtp` directly in the JSON response for testing. Account-level lockout after repeated failed password attempts is absent (only IP-based rate limiting exists). | Introduce per-user account lockouts (`failedLoginAttempts` and `lockUntil` in `User.js`) to defend against distributed brute-force attacks across rotating IPs. Restrict `devOtp` behind a dedicated, non-production environment flag. |
| **JWT (JSON Web Tokens)** | Dual-token authentication architecture in `utils/tokenUtils.js`: Short-lived Access Token (15-minute expiry) carrying `{ id, role }`, and long-lived Refresh Token (7-day expiry) stored in MongoDB for rotation and revocation. Verified via `authMiddleware` in `middleware/auth.js`. | Tokens are transmitted in headers and stored in client storage (AsyncStorage/localStorage). If used on the Web Admin without `HttpOnly` cookies, refresh tokens are exposed to client-side script access. Default secret fallbacks exist in `config/env.js`. | Store refresh tokens in `HttpOnly`, `SameSite=Strict`, `Secure` cookies for web clients. Throw a startup error if `JWT_SECRET` or `JWT_REFRESH_SECRET` uses fallback defaults in staging or production. |
| **RBAC (Role-Based Access Control)** | Granular role authorization via `rbac(...allowedRoles)` middleware (`middleware/rbac.js`). Enforces role segregation across `guest` (public read), `commuter` (file complaints, profile, AI assistant), and `admin` (fares, routes, complaints, audit logs). Object-level authorization prevents IDOR in `complaintController.js`. | In `userController.js`, `updateUserStatus` does not guard against an administrator accidentally deactivating their own active admin session. The `guest` role is listed in the user model enum, but guest access is mostly unauthenticated. | Add guard conditions preventing admin self-deactivation or self-demotion. Formalize permission-level access control (e.g. `fares:write`, `routes:write`) to support future intermediate roles (e.g. transit dispatchers). |
| **Database Security** | Mongoose ODM parameterizes all queries to prevent traditional SQL/NoSQL injections. Global `express-mongo-sanitize` middleware in `app.js` strips dangerous MongoDB operators (`$gt`, `$ne`, `$where`) from `req.body` and `req.params`. Strict schemas reject undeclared fields. | Search endpoints (`userController.js`, `routeController.js`) use `{ $regex: search, $options: 'i' }` without escaping regex metacharacters, opening potential ReDoS (Regular Expression Denial of Service). Connection pooling limits are not explicitly set in `db.js`. | Escape regex characters using an escape helper before querying MongoDB. Configure connection pooling parameters (`maxPoolSize: 50`, `serverSelectionTimeoutMS: 5000`, `autoIndex: false` in production) in `config/db.js`. |
| **API Security** | Global `helmet()` middleware sets HTTP security headers (CSP, X-Frame-Options, X-Content-Type-Options, etc.). CORS whitelist restricts client origins in production. Global XSS cleaning (`xss-clean`) sanitizes request bodies and parameters. Request body size is capped. | Global JSON body size limit is set to `10mb`, which is unnecessarily large for REST endpoints without file attachments. No HTTP Parameter Pollution (`hpp`) protection is installed. CORS does not specify preflight cache duration (`maxAge`). | Lower standard body parser limit to `100kb`, reserving large limits only for multipart/form-data upload routes. Install `hpp` middleware to prevent array-parameter pollution. Add `maxAge: 86400` to CORS config. |
| **Encryption** | Cryptographic one-way hashing for passwords and OTP codes via `bcryptjs`. JWT signed with HMAC-SHA256. API keys and database credentials stored exclusively in `.env` configuration, keeping secrets out of source code. | Sensitive commuter grievance narratives and phone numbers are stored in plaintext in MongoDB. Data in transit depends on external reverse proxy configuration for TLS termination (API runs locally on plain HTTP). | Enforce TLS 1.3 via reverse proxy (Nginx / Cloudflare) with automated HSTS headers. Apply field-level encryption (AES-256-GCM) for sensitive commuter personally identifiable information (PII). |
| **Error Handling** | Centralized error-handling middleware (`middleware/errorHandler.js`) formatting standard error responses via `apiResponse.js`. Maps Mongoose `ValidationError` (400), Duplicate Key `11000` (409), `CastError` (400), and JWT errors (401). Strips stack traces in production. | Node process lacks global exception handlers (`unhandledRejection` and `uncaughtException`), meaning unexpected errors could crash the Node runtime without graceful teardown. Error details are not logged to persistent files. | Add process-level error listeners in `server.js` for graceful shutdown and logging. Implement structured logging (e.g. Winston or Pino) with unique error tracking IDs returned to clients. |
| **Rate Limiting** | Uses `express-rate-limit` with three distinct tiers: `generalLimiter` (100 req/15 min), `authLimiter` (20 req/15 min on `/api/auth/*`), and `chatLimiter` (20 req/hour on AI assistant). Sets standard `RateLimit-*` HTTP response headers. | Uses default memory store (`MemoryStore`), which does not synchronize across clustered server instances or multiple container replicas. Express is not configured with `app.set('trust proxy', 1)` when running behind reverse proxies. | Configure `app.set('trust proxy', 1)` in Express to accurately identify client IPs behind load balancers. Migrate to Redis-backed rate limiting (`rate-limit-redis`) for clustered production deployments. |
| **Audit Logging** | Dedicated `AuditLog` collection and Mongoose model (`models/AuditLog.js`). Captures user ID, name, email, role, action, resource type, resource ID, IP address, user agent, and timestamp. Integrated into fare updates, route edits/deletes, user status changes, and complaint triage. Admin API provided (`GET /api/admin/audit-logs`). | `authController.js` imports the audit logger but does not record authentication events (successful logins, failed attempts, logouts, password resets). Audit logs stored in MongoDB lack immutability controls against admin tampering. | Log all authentication events (`AUTH_LOGIN_SUCCESS`, `AUTH_LOGIN_FAILURE`, `AUTH_LOGOUT`, `PASSWORD_RESET`). Protect the `AuditLog` model with Mongoose pre-hooks preventing updates or deletions to preserve audit trail integrity. |

### Part R Lab Deliverable — Reflection

#### Question:
> **What security vulnerability or weakness did you address in this laboratory, and how would failing to implement the security control affect your MongoDB-based final project?**

#### Comprehensive Response for SmartSakay Dagupan:

In this laboratory exercise, the primary vulnerabilities addressed centered on **unrestricted API endpoints, unsafe query construction (NoSQL Injection), plaintext credential storage, absence of Role-Based Access Control (RBAC), and missing audit trails**.

Applying these concepts directly to **SmartSakay Dagupan** reveals critical operational and security implications:

1. **Impact of Broken Authentication & Plaintext Passwords:**
   If SmartSakay Dagupan failed to implement modern password hashing (bcrypt with salt factor 12) and JWT authentication, any unauthorized database read (or accidental leak of database backups) would instantly compromise all commuter and administrator accounts. Commuters' login credentials, passwords, and personal details would be exposed in plaintext, violating the Philippine Data Privacy Act of 2012 (RA 10173).

2. **Impact of Missing Role-Based Access Control (RBAC):**
   In SmartSakay Dagupan, LTFRB-authorized fare rates and municipal transit routes directly impact the daily financial expenditure and travel safety of Dagupan commuters. If RBAC and the Principle of Least Privilege were absent, any authenticated regular commuter (or malicious actor registering a free commuter account) could issue `PUT /api/fares/:id` or `DELETE /api/routes/:id` requests, altering statutory fare matrices, injecting fraudulent fares, or deleting transit corridors. By enforcing `rbac('admin')` and object-level permission checks (e.g. commuters viewing only their own filed complaints), unauthorized operations are blocked at the middleware layer with `403 Forbidden`.

3. **Impact of Unsafe Database Queries (NoSQL Injection):**
   Accepting arbitrary request payloads directly into MongoDB queries (e.g. `User.findOne(req.body)`) enables NoSQL query operator injection attacks where an attacker submits `{"email": {"$gt": ""}, "password": {"$gt": ""}}`, allowing authentication bypass without knowing valid credentials. By sanitizing input with `express-mongo-sanitize`, validating structures through Joi, and explicitly extracting discrete fields (`{ email: email.toLowerCase() }`), the application ensures input untrustworthiness is treated as a fundamental design principle.

4. **Impact of Missing Rate Limiting and Audit Logging:**
   Without rate limiting on `/api/auth/login` and `/api/auth/verify-otp`, automated botnets could execute high-speed credential stuffing or brute-force 6-digit OTP codes within minutes. Furthermore, without an immutable audit logging mechanism (`AuditLog`), unauthorized modifications to public fare rates or commuter grievances could occur without accountability, leaving administrators with no forensic trail to identify the compromised account, IP address, or timeline of tampering.
