2. MERN Architecture

Describe how your project implements the MERN architecture, showing how React communicates with Express/Node.js and interacts with MongoDB via Mongoose.

SmartSakay Dagupan is architectured as a decoupled, multi-tier cloud application. The React 18 + Vite administrative SPA and React Native commuter client communicate via structured REST/HTTPS requests with an Express 5 application running on Node.js. The backend executes schema validation, JWT verification, and RBAC rules before interacting with MongoDB Atlas using Mongoose 9 Object-Data Modeling.

2.1 Request-Response Flow

Trace Scenario: Commuter Filing an Overcharge Grievance with Route and Vehicle Details.

Step What Happens in Our Application
1. React/UI Event The commuter selects incident category overcharging, inputs vehicle plate ABC-1234, selects route Downtown to Bonuan Tondaligan, and clicks "Submit Incident Report". Client state validates non-empty inputs and calls complaintService.createComplaint(payload).
2. HTTP Request Axios attaches the stored JWT Access Token in the Authorization: Bearer <token> header and dispatches an HTTPS POST request to /api/complaints with the JSON body.
3. Express Route Request passes global middleware (helmet, cors, generalLimiter, mongoSanitize). In complaintRoutes.js, authMiddleware verifies token integrity and attaches req.user; rbac('commuter') validates role permissions; validate(createComplaintSchema) ensures field validity.
4. Controller/Logic complaintController.createComplaint binds userId = req.user._id, sets default status to pending, sanitizes text inputs, and stages the document.
5. MongoDB Operation Mongoose executes await Complaint.create({...}). The document is validated against Mongoose schema constraints and persisted in the complaints collection in MongoDB Atlas.
6. API Response Controller returns standardized payload: { "success": true, "message": "Complaint submitted successfully", "data": { "_id": "...", "status": "pending" } } with HTTP status 201 Created.
7. UI Update The React UI catches the 201 response, displays a confirmation toast notification, resets the incident form, and prepends the new ticket to the commuter's "My Complaints" tracking screen.

4. Security Analysis of Our Project

Area Potential Risk in Our Project Impact Planned Control
Authentication Credential stuffing or brute-forcing 6-digit OTP codes on verification routes. Unauthorized account takeover, commuter impersonation, and fraudulent grievance submissions. Tiered rate limiting (authLimiter: 20 req/15 min), bcrypt hashing of OTP codes, 5-minute strict TTL, and 5-attempt lockout.
Authorization / RBAC Privilege escalation or IDOR where a commuter modifies LTFRB fare rates or views other commuters' complaints. Tampering with city-wide transit fares causing public disputes; exposure of sensitive commuter personal data. Enforce rbac('admin') on administrative routes; apply object-level ownership checks in complaint controllers.
Input Validation Malformed JSON bodies, non-numeric fares, or script payloads in route names and complaint narratives. Database errors, invalid calculations, or cross-site scripting vulnerabilities. Centralized Joi validation schemas enforcing data types, length boundaries, regex patterns, and string trimming.
Database NoSQL query injection via malicious MongoDB operators (e.g. {"$gt": ""}) in login or search queries. Authentication bypass without valid credentials; unauthorized extraction of database documents. Deploy express-mongo-sanitize globally; use Mongoose parameterized models; prohibit dynamic $where query clauses.
API API flooding or request flooding on heavy endpoints (AI chat, route directory). Server resource exhaustion, memory leaks, and service downtime for daily commuters. Global generalLimiter (100 req/15 min), chatLimiter (20 req/hour), and request payload size caps.
Passwords Storage of plaintext or weakly hashed passwords exposed during accidental database leaks. Catastrophic credential compromise across services; legal liability under RA 10173 (Data Privacy Act). Cryptographic hashing using bcryptjs with work factor 12 in Mongoose pre-save hooks; strip password hash in toJSON().
Deployment Insecure HTTP transmission exposing JWT tokens; accidental leakage of secret keys via Git commits. Man-in-the-middle token theft on public terminal Wi-Fi; full database takeover via leaked Atlas credentials. Enforce TLS 1.3 across all production hosts; inject secrets via environment dashboards; exclude .env in .gitignore.
Other Tampering with administrative audit records; absence of forensic traceability. Inability to hold rogue administrators accountable for illegal fare hikes or dismissed complaints. Dedicated AuditLog collection recording all mutations with actor ID, timestamp, action, and client IP address.

Synthesis and Reflection Questions

1. What changed when your application moved from local development to deployment?

When transitioning from local development to production deployment: (1) Transport Security: We moved from unencrypted local HTTP (localhost:5000) to TLS 1.3-encrypted HTTPS via cloud reverse proxies enforcing HSTS headers. (2) Database Isolation: We transitioned from standalone local MongoDB to a managed MongoDB Atlas M0 replica set in the AWS Singapore region with SCRAM-SHA-256 authentication and IP whitelisting. (3) CORS Hardening: Permissive development CORS policies were replaced with strict origin whitelisting. (4) Secret Isolation: Plaintext .env files were replaced with cloud platform environment key-vaults. (5) Error Sanitization: Internal stack traces were suppressed in production mode to prevent information leakage.

2. What security weakness did your testing reveal?

Our security testing uncovered three key vulnerabilities: (1) NoSQL Query Injection: Endpoints accepting request bodies directly into Mongoose filters were vulnerable to query operator injection (e.g. {"$gt": ""}) which could bypass authentication. (2) Parameter Handling: URL path parameters (such as :id) were not initially validated, causing raw Mongoose CastError exceptions. (3) Missing Auth Rate Limits: Endpoints like /api/auth/verify-otp lacked dedicated rate limiters, posing a risk of brute-force attacks on 6-digit OTP codes.

3. How did your group address the identified weakness?

We implemented three remediation layers: (1) Integrated express-mongo-sanitize globally in Express to strip all $ and . characters from incoming payloads, and explicitly destructured primitive fields in controllers. (2) Added centralized handling for CastError, ValidationError, and duplicate keys in errorHandler.js, returning clean 400 Bad Request responses with no stack traces. (3) Configured authLimiter via express-rate-limit to limit authentication attempts to 20 per 15 minutes, and hashed all stored OTP codes using bcryptjs with a 5-minute TTL.

4. What additional security improvement would you implement if given more development time?

With additional development time, we would implement: (1) Redis-Backed Distributed Rate Limiting: Use rate-limit-redis to share rate-limiting state across clustered server containers. (2) HttpOnly, SameSite=Strict Cookie Storage: Migrate refresh tokens to secure cookies to completely neutralize token theft via XSS. (3) Client-Side Field-Level Encryption (CSFLE): Implement AES-256 field-level encryption for sensitive commuter personal details in MongoDB. (4) Automated Account Lockout: Implement temporary account lockouts after 5 consecutive failed password attempts.
